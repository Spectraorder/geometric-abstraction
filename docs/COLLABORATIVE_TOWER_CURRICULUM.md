# From inventory stacking to stable human–robot towers

## Decision: learn placement repair before maximizing height

The end task is alternating construction: a human adds one block, the robot
observes the whole structure, corrects an unsafe placement if necessary, adds
one block, and hands the turn back. The robot should build as high as its
measured placement reach allows while keeping the tower stable after each turn.
Random scenes draw objects from the current 20-object pool (five shapes in four
colors). This pool currently includes cubes, rectangular prisms, slender prisms,
cylinders, and triangular prisms.

**The next learning experiment is short-stack repair after a simulated human
placement.** The seed skill is `policies/stack_inventory_cpu.py`. Its reported
50/50 reserved six-object result applies to a single red-prism-on-blue-cube
placement. It is not evidence of high-tower construction or repair of a prebuilt
stack. The new experiment must earn its own results.

Why start here:

| Candidate next step | Benefit | Why it is or is not first |
| --- | --- | --- |
| Repair an off-center top block on a short stack | Teaches observation, intervention, preservation of the foundation, and checking the result | **Chosen:** directly addresses imperfect human placement with a short, diagnosable action sequence |
| Maximize a mixed-shape tower immediately | Tests reach, object selection, support geometry, and long sequences | Too many new failure sources at once; an early fall hides whether perception, placement, shape choice, or reach failed |
| Add live alternating human turns immediately | Tests the intended interaction | First establish a repair skill and explicit handoff conditions in simulation; the current repository has no live human-turn controller |

The current perception code estimates initial height above the tabletop. That
assumption fails for objects already supported by another block. Its controller
also relocates the blue base, which would dismantle an existing tower. The LLM
must learn how to change those assumptions from images and execution feedback.
The experiment infrastructure defines the task and scores it; the recovery
controller is generated by the LLM through revisions of the existing source.

## First experiment: preserve or recenter

Each scene contains six objects: a blue cube, a red slender prism already on
that cube, and four randomly sampled distractors from the remaining inventory.
The tower location varies in a small reachable workspace; distractors initially
leave that workspace clear. Paired trials use the same scene with either a
centered target or an upright lateral offset of 6–8 mm in one of four
directions. This exceeds the 4 mm centering criterion while leaving time to
observe and regrasp. It is not yet an unstable, rapidly falling or randomly
tilted object. Preflight tests of 12.5–14 mm offsets collapsed before a normal
observe/grasp sequence could finish, so that harder regime is deferred until
basic repair works. The final evaluator is identical for every candidate.

The prebuilt pose represents a human turn completed before robot observation.
Only the reset routine sets those poses. Once the trial begins, corrections
must use camera observations, robot movements, grasps, releases, and physics.
No human avatar, live human input, pose correction oracle, or forced attachment
is part of this first experiment.

| Measure | Passing condition |
| --- | --- |
| Identity and support | Red slender prism upright on blue cube; cube on table; no support from distractors |
| Corrected alignment | Target/base horizontal center error at most 4 mm |
| Preserve foundation | Base displacement never exceeds 3 mm during robot execution |
| Preserve the prebuilt structure | Target never drops or is lowered to tabletop level; lift-and-reseat is allowed |
| Centered controls | Target displacement never exceeds 4 mm; do not disturb an already sound stack |
| Stability after release | Existing evaluator: upright within 8°, speed at most 15 mm/s, angular speed at most 0.1 rad/s, support COM margin at least 3 mm, and no robot contact |
| Final hold | Five seconds of checked stability and at most 3 mm drift after settling |
| Development set | Seeds 1501–1504, each centered and offset: **8 trials**, reported separately by case |
| Reserved set | Seeds 2501–2504, each centered and offset: **8 new trials**, run only after source freeze; never used for repairs |

Only the complete criterion counts as a pass. Loop v2 separately tracks verified
intermediate milestones to select the next experiment; the old absolute
centering score remains a diagnostic, not a selection criterion. Leaving an
already-centered stack alone must not be mistaken for learning to repair one.
Centered controls alone cannot meet the 8/8 target.

The learner receives side RGB-D, wrist RGB, calibration, robot proprioception,
robot-only IK previews, and reduced post-trial failure reasons and images.
True object poses, contacts, scene identities, and evaluator state remain
private during execution. The numerical helper source is available to the
learner as part of the seed policy. Random seed IDs are not online inputs.

## Learning and cost controls

The campaign uses the existing authenticated `gpt-6-astra` learner. Each call
proposes exact edits to a selected Python policy. The host validates and applies
those edits and executes eight physical trials. Loop v2 keeps a full-task
champion separately from a milestone-based exploration parent (details below).
No neural weights are trained. Policy controllers are still written by the LLM,
not replaced with a hand-authored repair controller.

This initial run has a **four-revision limit**, **80,000 reported input+output
token budget**, and one-hour Slurm wall-time allocation. It reserves 20,000
reported tokens before starting another call; individual call usage is only
known afterward, so this is not a strict billing cap. Images also consume
tokens. Exact edits reduce generated output compared with returning the whole
58 KB policy every round. One baseline and at most four candidate evaluations
cost at most 40 development rollouts; successful completion adds eight reserved
rollouts. An interrupted trial is archived, not overwritten. Model prompts,
edits, usage, outcomes, and every physical rollout remain on disk.

Stop when all eight development cases pass, freeze and validate once; otherwise
stop at the round/token/wall-time limit or after two v2 revisions without verified
progress, with the best measured candidate saved. Reserved-set failures are
marked `heldout_failed`, not successful completion, and are not fed into repairs.
A failure of the runner or a malformed model response is reported rather than
silently spending another model call. Reaching a budget does not mean the skill
has been learned.

## Reach and how many objects to supply

Do not pick a fixed maximum tower height from arm link length alone. The useful
limit depends on tower XY, payload dimensions, gripper orientation, approach
clearance, and the ability to withdraw without collision. A position-only IK
solution does not establish that a block can be placed safely.

`scripts/measure_tower_reach.py` scans 15 tabletop sites and tower heights in
10 mm increments, using the actual robot joint limits and the same robot-only
IK as the policy. It requires at most 3 mm tool position error and 8° gripper
tilt for both release and a 30 mm approach/withdraw clearance, using 30 mm and
60 mm payload heights and an assumed 30 mm tool-to-payload-center grasp offset.
The report is `outputs/inventory_repair_reach_02.json`.

The September 23 scan gave the following estimates with the current IK and
assumed grasp offset. Counts mean pieces needed to meet or exceed the height,
not a claim that the resulting discrete stack can be placed:

| Constraint in the sampled scan | Highest passing height above table | All-60-mm geometric count | All-30-mm geometric count |
| --- | --- | --- | --- |
| Release and 30 mm approach both within 8° tilt | 8 cm | 2 | 3 |
| Release within 8°; approach not certified | 11 cm | 2 | 4 |
| Position error only, ignoring tilt | 15 cm | 3 | 5 |

The 15 cm row is **not a safe stacking height**. Even the 8 cm row does not
certify a collision-free grasp path. The existing 9 cm cube-plus-prism result
also shows why the conservative approach assumption should not be mistaken for
an absolute arm limit. A first height experiment should provide at least
**four compatible pieces** (for example a cube base, two tall flat-top prisms,
and a spare); sample six or more total objects so distractors need not be used
as supports. One cube plus two 60 mm upright prisms gives 15 cm geometrically.
The policy must stop safely if it cannot place the next piece.

This is a sampled kinematic estimate, not a certified global reach maximum or
a collision-free manipulation result. Later tower trials must measure the
actual held-object offset and confirm a safe approach, release and retreat.
An IK solver failure must be reported as a planning failure until alternate
approaches and starts have been checked; it is not by itself proof that the arm
is physically out of reach.

For an estimated useful height H above the tabletop, the optimistic minimum
number of upright pieces is `ceil(H / 0.06)` because the tallest current piece
is 60 mm. For 30 mm cubes it is `ceil(H / 0.03)`. Count the base as one object.
These are geometric counts, not guarantees of stable stacking. Only four cubes
exist in the pool; taller towers need other support-compatible pieces. Supply
at least one extra compatible piece beyond the estimated minimum to test the
next placement at the reach boundary. A random sample with too few usable
pieces ends as **inventory exhausted**, not **reach limit reached**.

## Curriculum after short-stack repair

1. **Validate recovery and restraint.** Finish centered/offset pairs with unseen
   seeds; then widen offsets, introduce small yaw/tilt and occlusion, and test
   larger distractor counts. Distinguish marginal-but-standing placements from
   actively collapsing structures; the latter need separate reaction-time tests.
2. **Grow a regular tower.** Add one compatible block at a time. Observe the
   entire support chain, wait for settling after every release, and attempt
   repair before continuing. Start with three levels, then four, then higher.
3. **Mixed shapes and measured reach.** Sample larger subsets from the 20-object
   pool and learn selection, orientation, and ordering. Triangular prisms cannot
   be treated as axis-aligned boxes with flat top support. Use shape-appropriate
   contact/support checks, and separate unsupported geometry, no safe plan,
   inventory exhaustion, perception failure and verified reach boundary.
4. **Alternating simulated human and robot turns.** A human-turn simulator or
   teleoperation adds one block with controlled placement errors. The robot
   re-observes, repairs if necessary, adds one block, withdraws and signals a
   handoff. Preserve turn history and test the full tower after each turn.
5. **Human interaction on hardware.** Add an explicit turn/stop interface and
   validate hardware motion limits and human access before transferring the
   simulation policy. This is a later experiment, not a result of the first run.

For the height curriculum, report stable tower height, number of placed blocks,
success per turn, minimum support margin, falls, unnecessary interventions,
repair success, reach/stop reason, usable inventory remaining, simulation time,
LLM tokens and total rollouts. Use reserved object/layout/perturbation samples
after selection; do not describe training success as general reliability.

## Learning-loop correction (September 24, 2026)

The subsequent resume completed revisions 3 and 4. The baseline and **all four
revisions** still passed **4/4 centered controls and 0/4 offset repairs**; usage
reached 134,818 reported input/output tokens. None of the 16 offset trials from
the four generated revisions issued a gripper-close command. These runs did
not demonstrate grasping or pose correction. The original inventory policy
remained `best_policy.py` because no revision improved full-task success.

The failures were before grasping: supported-object identification rejected
candidates, and later motion proposals failed reach checks. Two shortcomings
made repeated attempts unproductive: unsuccessful source changes were not
retained as the next parent, and feedback lacked actual IK replies and explicit
intermediate evidence. Calling `camera()` and `camera('side')` was also mistaken
for multiview sensing; they are the same fixed RGB-D camera. Only wrist RGB is
a distinct view, without a depth channel.

Loop v2 changes the learning infrastructure without changing the final pass
criteria or injecting corrected object poses:

| Stage | Required evidence on offset trials | What it does not prove |
| --- | --- | --- |
| Identify | Sensor-derived base/target centers within 10 mm and target dimensions within 8 mm of private evaluator measurements | A safe grasp or repaired stack |
| Plan | Three recorded, matching IK previews: approach, grasp, lift; position error ≤3 mm, tilt ≤15°, target-local geometry and approach/lift clearances checked | Collision-free trajectories or successful execution |
| Grasp | After identification/planning, target lifted ≥5 mm with both jaw contacts continuously for ≥0.1 s; foundation preserved | Successful reseating and release |
| Repair | All original alignment, contact, foundation, release and five-second stability criteria pass | Generalization beyond evaluated scenes |

Policies log measurements through `api.report(...)`, which always returns
`None` for valid reports. Private verification is supplied only after execution;
the robot cannot query true object poses or use an online success oracle.
Closing an empty gripper and self-reporting success earn no grasp credit.
Old recordings without the new checks remain **unverified**, not retroactively
credited from notes or requested motions.

Candidate selection first requires preserved centered controls and no offset
collapse, excessive foundation drift, or unhandled policy error:

- `best_policy.py`: full-task champion; ties preserve the earlier champion.
  `best_policy.json` explicitly says whether any offset repair was demonstrated.
- `exploration_policy.py`: next-edit parent, ranked by offset passes, then
  verified grasp, planning, identification, and grasp-backed centering improvement.
  A 1 mm deadband excludes small settling changes. Equal evidence favors the
  latest eligible revision so failed experiments are not always restarted from
  the original source.
- `milestones.json`: best eligible candidate for each verified stage. Partial
  skills are retained without claiming they are successful repair policies.
- `best_repair_trial.txt`: written only for a successful **offset** trial.
  An old `best_trial.txt` may identify a centered control and is not repair evidence.

The next prompt includes the exploration source, recent actual source diffs,
numeric rejection logs, recorded IK results, and post-trial milestone checks.
Unreferenced legacy functions may be omitted from prompt display only; saved
source and exact-edit application remain intact. Full prompts and raw evidence
are retained, with an 85,000-character context cap checked before a model call.
This reduces unnecessary retransmission but does not guarantee cheap calls;
images, reasoning, and model tokenization still contribute to usage.

The default `--stagnation-rounds 2` stops further proposals after two new v2
revisions without verified improvement. `--stagnation-rounds 0` explicitly
disables that guard. Round/token limits remain cumulative across resumes. A
saved, already-paid proposal can finish testing even if the new-call budget is
exhausted; the loop never silently purchases a replacement for an incomplete
proposal. A campaign lock prevents concurrent learners, and interruption or
timeout terminates the active child process group.

Direct `progress.log` and `progress.json` writes provide phase, per-trial results,
and approximately 15-second heartbeats while waiting for model/trial processes.
They do not depend on Slurm stdout routing. A heartbeat means the process is
still being awaited, not proof that it is making learning progress.
