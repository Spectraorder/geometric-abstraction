# Luna 快决策 × Astra 慢规划：如何读这次实验

这次我们想回答：**同一个机器人任务里，快模型和慢模型各需要多少推理投入？** 新实验不再调用 Jev。Luna 负责选择下一步，Astra 负责制定计划，以及在必要时修订计划。

[公开英文页面](https://aspire-so100-recovery.vercel.app/luna-astra/)可以查看配置矩阵、对照结果、每次尝试的录像和决策过程。[完整英文说明](LUNA_ASTRA_README.md)给出运行方法与实验边界。

## 机器人实际做了什么

任务还是蓝—红—绿三层塔。机器人先用 RGB-D 检查桌面和目标积木。Astra 写出条件式计划；Luna 决定开始、重新观察、交给 Astra 修订，或停止。确认可执行以后，所有组都运行同一份已经冻结的视觉搭塔技能。

**此次模型只参与动作开始前的观察阶段。** 抓取、放置中的已有重试来自冻结技能，不是本次模型新学出来的能力。录像来自真实执行过的仿真状态，也没有用生成视频替代实验。

## 这批结果说明了什么

三个纯 Luna 对照都通过 3/3，累计模型等待为 87.51–94.79 秒；混合配置累计等待为 137.60–231.98 秒，并有三个配置在短暂遮挡中失败。纯 Astra 的四个档位也都通过 3/3。

对于当前这个简单的初始观察关卡，新增慢规划没有显示出质量收益。计划表述的歧义，以及最后一次观察后缺少恢复预算，是应该先处理的问题。这个结果不代表 Luna 足以解决更长流程、更复杂的操作任务，也不能用这几个案例给模型档位做稳定排名。

## 一共有多少组

- 混合组：Luna 低／中／高 × Astra 低／中／高／极高，共 12 个配置。
- 纯 Luna：低／中／高，共 3 个配置，使用固定任务描述，不调用慢模型。
- 纯 Astra：低／中／高／极高，共 4 个配置，同一档位同时用于计划和决策。

19 个配置各跑 3 个相同的场景组合，共 **57 次正式试验**。其中 Astra high 这一列对应你提出的默认慢模型设置。

| 场景 | 随机种子 | 怎样才算通过 |
|---|---:|---|
| 正常可见 | 4601 | 完成三层塔 |
| 蓝色目标短暂遮挡 0.35 仿真秒 | 4602 | 重新观察后完成三层塔 |
| 蓝色目标一直被遮挡 | 4603 | 明确停止，并且没有机械臂或夹爪动作 |

各模型配置面对同一组场景，便于配对比较；但每种情况只有一个种子，不能据此判断普遍成功率。场景间种子不同，因此也不能把所有差别都归因于遮挡。

正式批次之前，单独运行过一次 Luna subagent 观察探针，以及一次 Luna low＋Astra high 闭环连通性试验；它们不计入上述 57 次。

## subagent 如何运行

第一份观察探针通过 `collaboration.spawn_agent` 真正启动 Luna low，未继承父会话，不使用工具。为了批量复现，正式试验每次模型调用启动一个独立的 Codex 子会话，明确指定 Luna 或 Astra 和推理档位，关闭工具，要求结构化输出。模型没有父助手的完整聊天记录，也不读取仓库或其他尝试的结果。

模型只看到当前视觉提取出的摘要：时间、观察版本、可见颜色、桌面拟合、抓取标志和剩余次数。物体真值、接触信息、故障计划和最终成功判定留在私有执行器中。

## 网页上的数字怎么读

**完成搭塔**与**正确停止**是不同的指标。持续遮挡时，静止不动可能是通过停止测试；它不是“搭塔成功”。

**通过 3/3**表示两个搭塔检查和一个停止检查通过，不等于真实任务上有 100% 成功率。

**模型等待**是全部模型调用的实际耗时之和，包含客户端启动和排队。**仿真时间**不包含等待模型的时间。录像按 3 倍速播放，也省略模型等待，所以不能用录像长短比较效率。

**规则一致性**是模型建议是否符合预先写好的可见性规则；这不是独立标注的决策准确率。**慢模型修订次数**只代表调用发生，不能据此宣称恢复成功。

Token 使用量来自实际返回值；缓存输入是输入的一部分，不能重复相加。当前使用订阅客户端，**美元费用未知**，不会填写成零或宣布哪组更便宜。

两次试验在同一台 Mac 上并发，执行顺序固定随机化。这里测到的是这个运行环境中的耗时，尚未排除机器负载和服务端波动。

## 如何复现

安装项目依赖并保证 Codex 已登录、能够访问这两个模型后，在项目目录运行：

```bash
uv sync
uv run python scripts/run_luna_astra_trial.py \
  --mode luna_hybrid --fast-effort medium --slow-effort high \
  --fault transient_occlusion --seed 4602 \
  --output outputs/luna_astra_example

uv run python scripts/render_luna_astra_trial.py \
  --trial outputs/luna_astra_example --endpoint tower_completion --speed 3 --fps 12
```

完整批次和网页导出命令见英文说明。每次尝试必须使用新的输出目录；失败、超时和无返回用量的调用都会保留，不会静默重跑直到成功。

## 一个值得看的失败案例

Luna low＋Astra medium 在短暂遮挡场景中，前两次正确选择重新观察；第三次三种颜色都已可见，却以 0.99 的置信度请求升级。Astra 随后修订计划，但剩余观察次数为零，执行器要求修订后重新观察，因此只能停止。

初始计划仍保留“蓝色目标目前缺失”的旧描述。这是可观察到的计划与当前状态不一致，不能直接证明模型内部为什么这样决策。该失败还暴露了一个协议限制：**最后一次观察后升级，没有剩余恢复空间**。这批实验没有中途修改规则或重跑来消除失败。Luna high＋Astra xhigh 在同一场景也出现了目标可见后升级并停止的情况；至少在这些尝试中，单纯提高推理投入没有解决协议歧义。

## 如何继续验证“快慢系统自纠正”

先把瞬时场景事实与条件计划明确分开，并为应用修订计划预留有上限的观察预算；这应作为新协议，重新跑全套对照，不能混入本批结果。然后在抓取后、放置后接入模型决策，注入滑落等异常，记录完整链条：新观察发现异常 → Astra 给出有用的新计划 → Luna 根据新证据决策 → 成功恢复。随后加入禁止重规划的消融、固定规则对照，以及更多独立场景和重复试验。

当前初始观察关卡里的重新观察，不能代替这条更强的实验结论。
